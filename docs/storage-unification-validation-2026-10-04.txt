Storage unification - local implementation and validation, 2026-10-04

Status

The production refactor is implemented. No regression was observed in the
completed comparisons. This is NOT an all-green release qualification: the
existing test failures and outstanding manual checks below remain explicit.
During this validation no version, release workflow, packaging, tag or remote
branch was changed. The tested binaries identified as 1.3.3-rc5; that existing
tag does not contain this work. The subsequent test release is 1.4.0-rc1.

Baseline and implementation

- af99b94 captures the previously uncommitted external Windows NTFS support,
  its tests, and the corrected physical-unplug validation record. It is the
  comparison baseline, rather than the older rc5 tag alone.
- d83e01e adds cross-platform policy characterization before extraction.
- ca68426 centralizes the checked 256 MiB recovery reserve and volume eligibility.
- 1d7a408 extracts the internal probe context/platform seam and Windows flow.
- 1c33d33 binds POSIX to that same flow without replacing its storage resolver.
- 8f5dff2 adds locator, permission, failure-boundary and storage-selection tests.
- Additional Unicode tests exercise both locator migration and native probing.

The common flow now owns locator priority, pinned-vault adoption, manifest
matching, capacity/classification checks, creation-boundary rechecks, locator
repair and successful BackendProbeResult construction. Platform adapters retain
native access checks, directory preparation, volume inspection and free space.
There is one production flow, not a runtime switch between old and new versions.

Unchanged contracts:
- Public classify_storage(), TransactionBackend::probe() and BackendProbeResult.
- Installation/volume identities, patch-plan hash, case rules and storage bases.
- Windows and POSIX selection rules, including conflicting private/library state.
- On-disk/protocol formats, locking, recovery, migration and cleanup ordering.
- Native filesystem primitives, link handling and PreparedStorageContext handles.
- Repair-sensitive reasons, including vault-owner-or-dacl, active-vault-* and
  state-home-not-controlled. ContentCatalog repair prefix behavior is unchanged.
- External Windows NTFS remains Automatic with independent internal recovery;
  external exFAT remains Persistent only. No new filesystem was enabled here.

Shared messages retain native details; POSIX success/warning and capacity text
is more explicit. POSIX volume eligibility now uses the common helper: its
unchanged inspector only sets native_durability for local, internal trusted
filesystems, so the additional explicit local/internal predicates do not change
any volume returned by that inspector. No extra hash or diagnostic probe is added.

Compared with af99b94, core production code is 39 lines smaller, including the
new internal interface. Most added lines are regression tests, not product logic.
Foreign changes and the untracked third_party/f4se directory were not included.
Countdown and local orchestration scripts remain ignored under build/.

External NTFS and performance

G: remains the existing isolated Intenso SRS_TEST NTFS fixture. No reformatting.
Baseline/current probe output agrees on mode, volume identity and storage paths.
Repeated downgrade/source restore and cleanup passed. Five injected terminations
also passed fresh-process recovery followed by another idempotent recovery:
  activation: replace.after-source-move, replace.after-rename
  restoration: replace.after-source-move, replace.after-rename, remove-tree.before
The final source state is restored and its active recovery vault is removed.

The user-operated physical unplug before this refactor is documented in
external-ntfs-validation-2026-10-04.txt. It passed fallback recovery after
reconnection. These new process-termination tests are NOT another physical
unplug/power-loss test. A repeat with the current code requires user coordination.

Five cold-SRS-cache and five warm-SRS-cache activations per implementation:
  baseline cold ms:   11202, 9072, 7421, 6984, 6585  (median 7421)
  refactor cold ms:    6791, 6638, 7812, 9703, 33870 (median 7812; +5.27%)
  baseline warm ms:    4984, 2485, 2673, 3462, 5019  (median 3462)
  refactor warm ms:    2403, 5441, 9684, 2353, 2423  (median 2423; -30.01%)
These are SRS transaction timings, not game startup time. Cold means an empty
SRS target cache, not flushed OS caches. Previous caches were moved aside under
the isolated test root, not deleted. Restore/source verification follows every
activation. The measured median threshold is met, but background builds and
large I/O outliers make this insufficient evidence of a speedup. A quiet repeat
would improve confidence; no performance gain is claimed.
