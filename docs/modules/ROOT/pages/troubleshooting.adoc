= Troubleshooting

Skyrim Runtime Swapper fails closed when it cannot prove that a write is recoverable.
A blocked launch is preferable to starting Skyrim with a mixed or unverifiable runtime.

== Collect diagnostics first

Use *Copy logs* in the error dialog whenever it is available, then paste the result into your support report or save it as a text attachment.
The copied diagnostics include the SRS log and the newest available SKSE log when readable.
An SKSE log may belong to an older attempt; check its timestamp rather than assuming it came from the failed SRS launch.

The primary log is stored at:

....
Documents\My Games\Skyrim Special Edition\SKSE\SkyrimRuntimeSwapper.log
....

This uses the Windows Documents location, including any configured redirection.
Under Wine or Proton, it is the Documents location in the prefix that runs SKSE, not necessarily your native Linux `~/Documents` directory.

When reporting a problem, include:

* The complete SRS log, or the affected session's header and all entries carrying the same `session` ID
* The exact SRS package name
* Mod manager and deployment mode
* Operating system and Wine or Proton version
* Game filesystem and whether the drive is internal, external, or removable
* The newest `skse64_loader.log` and `skse64.log`
* What happened immediately before the failure, including a crash or forced shutdown

IMPORTANT: Do not delete the recovery vault, locator, journal, or transaction workspace before collecting the log.

=== Distinguish launches and watchers

Current session headers include `log-format=2`.
Diagnostic entries carry:

* `run`: the ID of the SRS process that wrote the entry;
* `session`: the shared ID linking a primary launch and its watcher; and
* `parent`: the run that started the watcher, or `none` for a primary run.

The watcher has its own `run` ID and `operation=session-watcher`, but shares the launch's `session` ID.
Opening the manual control panel starts a separate primary run with `operation=manual-gui`.
Multi-line details belong to the prefixed entry above them.

Use these IDs to group entries even when output from different processes is interleaved.
Older logs without these IDs cannot be correlated with the same certainty.

[#log-history]
=== Log history and older logs

SRS keeps one log file, retaining the latest 30 primary starts and the output following those retained starts.
Watcher headers do not count as additional primary starts; manual control-panel starts do.
Older history is trimmed when another primary start is logged.

When the new format starts, old contents without `log-format=2` are replaced rather than mixed with correlated entries.
SRS also removes its legacy log at:

....
%LOCALAPPDATA%\Skyrim Special Edition\SKSE\SkyrimRuntimeSwapper.log
....

Save a copy before updating or repeatedly retrying if you need an older failure for a support report.
This log cleanup does not delete SKSE's own logs, runtime backups, or recovery journals.

== The Collection reports the wrong installed Skyrim version

This warning comes from the manager's Collection compatibility check, before SRS switches the runtime.
If Skyrim is correctly installed as 1.7.104 but the Collection expects 1.6.1170 or 1.5.97, ask the curator to set the Collection's game-version requirement to the source version.
The SRS package and SKSE should still target the older runtime.

Do not manually downgrade or replace the Collection's files just to silence this warning.
Compare the actual installed version and the Collection requirement first; other version mismatches may need a different fix.
See xref:curators.adoc#collection-game-version[Collection game-version settings].

== SRS does not appear before the SKSE version error

Symptoms include:

* SKSE reports that Skyrim 1.7.104 is newer than the installed SKSE version.
* No Skyrim Runtime Swapper dialog appears.
* No new SRS session is written to the log.

Check:

. `version.dll` is beside `SkyrimSE.exe`, not under `Data`.
. Only one mod supplies the active `version.dll` proxy.
. The launched executable is the intended `skse64_loader.exe`.
. The mod manager actually deployed the root files.
. Proton Experimental receives the override described in xref:proton.adoc[].

== SKSE reports "Couldn't retrieve EXE version information"

This usually means SRS stopped the launch after a failed or incomplete runtime operation.
The SKSE message is a consequence, not the root cause.

Read the preceding SRS dialog and the latest SRS log entry.
Resolve that failure before troubleshooting SKSE itself.

== Source file or source hash is not recognized

For patching, SRS expects the exact managed Skyrim 1.7.104 source files recorded by the package.
Files already matching the package's target hashes are also recognized.
An already-downgraded executable is not itself an error, but its other managed files must match the selected profile too.

Before replacing files, collect the log and resolve or report any pending SRS recovery state.
Steam verification changes the installed game files and should not be the first response to an unavailable recovery vault.

If the log identifies an unknown or modified source file and no SRS recovery is pending:

. Restore or purge the mod-manager deployment so vanilla files are no longer replaced by a stale VFS, symlink, hard-link, or overwrite layer.
. Run Steam's *Verify integrity of game files* action.
. Redeploy the mod setup once verification completes.
. Launch through SKSE again.

If Steam reports no problem but SRS still rejects a linked file, include the logged SHA-256, link type, and effective link target.
The mod manager may be exposing a stale copy from `Data_Core`, a staging directory, or an overwrite layer that Steam did not replace.

For xref:boaw_clean.adoc[BoAW-Clean], a master cleaned separately with SSEEdit is not necessarily a supported input.
Use the logged hashes to distinguish an exact supported target from a different cleaned or modified file.
`Actual SHA-256: <unavailable>` means SRS could not obtain a hash at that stage; it is not proof that the file was cleaned or has different contents.

Do not remove Beafarmer just to bypass recovery. It is optional only when the transaction's initial selection excludes it; once selected, its recorded recovery state must be respected.

== A staged runtime file failed verification

The dialog and log identify the live file, staged object, expected source hash, expected target hash, actual hash when available, patch hash, I/O stage, and native error.

Check:

* Available space on the game and recovery volumes
* Read-only filesystem or file attributes
* Device errors or disconnection
* Whether a VFS or sync process changed the staged object during the operation
* Whether all SRS files came from the same release archive

SRS includes a deterministic fallback for stale FUSE-backed HDiffPatch output metadata.
If the failure persists, submit the complete log instead of disabling VFS safety or bypassing hash verification.

== Persistent downgrade is required

This is expected on external, removable, exFAT, or uncertain local storage.

. Read the game-volume and recovery-vault descriptions.
. Continue only if the displayed vault is available and should remain available.
. Restore later by opening `SkyrimRuntimeSwapper.exe` and selecting *Restore Skyrim 1.7.104*.

Persistent with warning additionally requires explicit acceptance because the game filesystem could not be fully classified.

== Downgrade is not recoverable

The dialog shows a human-readable message and a stable *Technical reason*.

[cols="2,3",options="header"]
|===
|Technical reason
|Meaning and next step

|`network-target`
|The game is on a network share. Use supported local storage.

|`target-volume-unrecoverable`
|The target is unavailable, non-local, or lacks an identity SRS can verify. The combined message does not prove that it is network storage. Check the logged filesystem and mount; native ZFS datasets are currently unsupported. See xref:linux.adoc#zfs[ZFS support status].

|`unstable-target-identity` or `target-installation-identity-unavailable`
|SRS cannot bind recovery to the physical target. Use a filesystem or device with a stable identity.

|`independent-vault-required`
|The game target needs recovery on another durable device, but the automatic vault resolves to the same volume. Move Skyrim to trusted internal storage or make a suitable internal recovery volume available.

|`vault-volume-not-durable`
|The automatic recovery location is not on internal NTFS for Windows or internal ext4, XFS, or Btrfs for Linux.

|`vault-insufficient-space`
|Free space including the safety reserve is insufficient. Free space on the displayed recovery volume and retry.

|`vault-owner-or-dacl` or `vault-owner-or-mode`
|The SRS vault is not exclusively controlled by the current user. Do not weaken the check; correct ownership only for the displayed SRS directory.

|`unsafe-native-installation-lock`
|SRS cannot safely establish the installation lock. Since version 1.2.2, SRS can use private user-state storage for fresh installations in group-writable Linux Steam libraries. Existing unsafe or conflicting state can still block startup; preserve it and report the exact logged paths.

|`vault-parent-reparse` or `vault-parent-symlink`
|The automatically resolved vault hierarchy contains an unsafe redirection. Remove or correct the unexpected redirection without deleting active recovery data.

|`active-vault-directory-missing`, `active-vault-manifest-missing`, or `active-vault-unavailable`
|A recorded active vault is missing or changed. Reconnect the original volume or restore the original vault. SRS intentionally refuses to select a replacement silently.

|`prepared-storage-identity-changed`
|A file, mount, link, or volume changed after preparation. Stop other deployment or synchronization activity and retry from a stable layout.

|`wine-native-sidecar-required`
|The verified Linux helper could not be used. Redeploy the complete package and check `SkyrimRuntimeSwapper.Native` permissions.

|`content-catalog:<reason>`
|The user-specific ContentCatalog state cannot be recovered safely. The suffix identifies the underlying storage failure.
|===

== Linux state directory is not controlled by the user

Do not recursively change permissions on `/home`, `/var/home`, the Steam library, or the game directory.

Capture:

....
stat -c '%A %U %G %n' "/replace/with/the/displayed/path"
findmnt -T "/replace/with/the/displayed/path" -o TARGET,SOURCE,FSTYPE,OPTIONS
....

Replace the quoted placeholder with the actual path from the error.
SRS uses verified Steam-library transaction storage when safe and does not require an unrelated XDG state directory for that operation.
Since version 1.2.2, SRS instead selects validated private user-state storage for fresh installations where group-writable library parents cannot safely host the lock.
If both locations contain state, or an existing state location is unsafe, SRS blocks instead of silently starting with a new vault.
If the error remains, provide the current SRS log and the output above.

[#native-helper-permissions]
== Native helper permission error

The package should preserve executable mode and SRS attempts safe repair.
If the manager extracted the helper without execute permission and automatic repair fails:

....
chmod 700 SkyrimRuntimeSwapper.Native
....

Apply this only to the packaged helper in the Skyrim root.

== Recovery after a crash or forced shutdown

. Reconnect every volume that was present during the transaction.
. Do not delete SRS state.
. Start the same installed SRS package through SKSE or open `SkyrimRuntimeSwapper.exe`.
. Allow recovery to finish before purging or redeploying the mod manager.

If recovery blocks, copy the logs and preserve the displayed vault path.

[#inconsistent-recovery]
== Inconsistent recovery markers

`code=34 (journal-corrupt)` or "The persistent recovery markers are inconsistent" means SRS cannot reconcile its stored transaction records.
It does not, by itself, prove that the current game files are damaged.
Some 1.2.2 RC attempts and a mixed-state BoAW-Clean recovery in 1.2.2 can leave this state.
Version 1.2.3 prevents the latter by saving the optional-file selection before creating the recovery journal; it does not automatically discard or repair already-inconsistent journals.

. Save the complete log and report the exact package version and profile.
. Close Skyrim, SKSE and SRS, and stop any mod-manager deployment.
. Keep the recovery vault and transaction workspace intact while support checks whether a restore is still needed.
. Only after the original source files are confirmed restored, and support has identified the exact installation-specific folders, archive or rename the obsolete state as directed. Keep those backups rather than deleting them.

The relevant paths are `recovery-vault` and `transaction-work` in that installation's log; an older `.skyrim-runtime-swapper` folder inside the game directory may also contain state.
Do not copy installation IDs or paths from somebody else's report, and do not reset only one linked state folder before launching again.
Leave game files, `RuntimeSwap`, the target cache and coordination lock untouched unless support specifically identifies a separate problem.

WARNING: Steam verification restores Steam-managed game files, not SRS recovery records or every file exposed by a mod manager. Never treat verification alone as permission to delete recovery data.

A successful reset addresses the obsolete records, not the underlying cause of every recovery failure.
Confirm a new activation and its matching watcher restore in the log before considering the case resolved.

[#cleanup-pending]
== Source verified, but recovery cleanup remains pending

This means restoration and cleanup are separate: the source may already be verified while SRS still needs to preserve conflict files or finish removing transaction metadata.
Since version 1.2.2, SRS can archive verified conflicts outside the active vault before retiring it; see xref:safety_recovery.adoc#conflict-archive[Conflict archives].

If the current release still blocks, keep the recovery data, check the logged storage error and provide the complete log.
Do not remove the vault just because the message says the source is verified.

== Confirm a complete automatic cycle in the log

A successful `prepare-launch` entry with `code=0 (success)` and `lifecycle-state=target_active` confirms activation.
It does not confirm that restoration has happened yet.
For a session in which SRS switched the runtime, look for the matching watcher's "The installation is in a verified source state" entry after Skyrim closes.
Use the shared `session` ID to connect the two.

`target-cache=10/10`, for example, means all ten selected target objects were reused from cache. It is not a count of tests or a replacement for the restore result.

== Amethyst reports a stale snapshot generation

An error such as:

....
snapshot generation 4 is stale; current generation is 5
....

comes from Amethyst's FileGraph changing during deployment planning.
Wait for its scan or refresh to finish and deploy again.
Restart Amethyst if it repeats.
The stale-generation guard runs before SRS deployment.

== A second launch waits or is rejected

SRS holds a per-installation coordination lock through activation and restore.
A new launch waits for or refuses to overlap an active transaction.

Wait for the prior Skyrim process and watcher to finish.
Do not remove the lock file while either process is still active.
